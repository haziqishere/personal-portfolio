## Understanding Lakehouse

Data lakehouse is basically open data management architecture that combine
the benefit cheap and flexible storage of Data lake while having ACID
capabilities of Data warehouse.

In data warehouse, data is already cleaned, integrated and processed since
storage is expensive. The data quality management & data governance usually
done here so downstream users can already use it for their use-cases.
However DW is not suitable for ad-hoc task since it impose strict schema.
This is where Data lake comes in. To put it simply, a data lake is where you
stores raw data in form of structured, semi-structured or unstructured in
which you can think of processing part later.

> A data lakehouse attempts to get the best of both worlds. It allows the
> storage of raw data like a data lake, while also facilitating the option
> for preprocessed, structured data like a warehouse. This combination can
> improve processing time and efficiency without compromising flexibility.
> — Databricks

The main benefit of lakehouse is:

- **Support schema evolution.** Unlike Data warehouse, a lakehouse does not restricted to lock-schema. Instead, we are able to do changes in the schema without rerunning the whole pipeline.
- **Transactional consistency** since it supports ACID operations.
- **Time travel and role-back** since it also holds snapshots.

Lakehouse achieves these by storing flat-files (such as parquet or CSV) in
object storage (such as S3). Then we would have a open table format which is
Apache Iceberg. Iceberg basically is an abstraction between your flat-files
and storage layer by handling both data and metadata for your table. We
mainly interact with the metadata manifest in form of Iceberg table.

Then, we have catalog layer that handle high-level versioning of schema and
table. A key feature of Project Nessie is that it has git-like version
control of the data.

I want to highlight that Iceberg at metadata layer will store detailed
metadata about datasets, including schema information, table definitions,
and partition details. In contrast, catalog will organize and manage
datasets, providing a high-level structure for databases and tables which
enable data discovery, access control, and governance.

## Architecture

Today I will be reviewing a Data Lakehouse project with query engine and
building data pipelines. After that completed, we will provision a BI
platform which is Metabase and perform analytics of processed data. Below is
the high-level overview of the project:

We will use Apache Airflow to orchestrate our batch pipelines. The pipeline
ingest the data from flat-files into landing database. Then processing and
transformation, it will use SQL logic that runs via dbt with Trino query
engine. The data will be sequently transform and process to staging
database then finally to curated database. The tables in curated will be
cleaned data that is ready to be use for analytics. Finally, Metabase
container will be provision to query curated database for analytics.

## Setting Up Local Data Infrastructure

For our lakehouse, as mentioned there are 3 layers which include catalog
layer, metadata layer and data layer. Below are our tech stacks in building
local data lakehouse.

MinIO is local alternative to other object storage such as S3. We store our
flat-files into MinIO which in this case is parquet files. Of course, you
may opt for CSV if you prefer; however, Parquet files have been the de
facto standard for storing analytics structured data in data lakes and
warehouses. You can easily spins up MinIO container via docker-compose as
below:

```yaml
services:
  minio:
    image: minio/minio
    container_name: minio
    environment:
      MINIO_REGION_NAME: ap-southeast-1
      MINIO_REGION: ap-southeast-1
      MINIO_DOMAIN: minio
      MINIO_ROOT_USER: ${USERNAME}
      MINIO_ROOT_PASSWORD: ${PASSWORD}
    ports:
      - "9000:9000"
      - "9001:9001"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9000/minio/health/live"]
      interval: 30s
      timeout: 20s
      retries: 3
```

For catalog, we will be using Nessie catalog. It is an open-source,
transactional catalog for data lakes that provides Git-like version control
for data tables, allowing users to branch, commit, and tag changes. Because
of this versioning model, you can:

- Track and manage schema or data changes in a controlled, auditable way.
- Easily update or evolve table schemas through commits to the catalog.
- Revert or "roll back" to previous versions or branches, similar to Git, if you need to undo or inspect changes.

You can also easily spins-up nessie-catalog container into via
docker-compose as below:

```yaml
services:
  nessie-catalog:
    image: projectnessie/nessie:0.76.6
    container_name: nessie-catalog
    ports:
      - "19120:19120"
```

We will go through how do we create iceberg metadata layers later.

Now, we had setup the storage. However, if we are going to create table,
process and transform table we need a way perform query. That is why we
need a query engine and transformation framework. For query engine we will
be using Trino. Trino is SQL-friendly distributed query engine that can be
set up in a cluster. It physically reads/writes the Iceberg data. For
transformation framework, we will be using dbt. It serves as to organises
transformation logic into modular SQL files that later being ran. Below is
what we would have:

In a Trino cluster, you can specify one node to be the coordinator node and
the rest be workers node. The reason it is advantageous to have 1
coordinator node is consistent query planning. Below is how you can spin-up
trino clusters via docker-compose:

```yaml
services:
  trino-coordinator:
    image: trinodb/trino:476
    container_name: trino-coordinator
    ports:
      - "8080:8080"
    volumes:
      - ../trino_config/coordinator/config.properties:/etc/trino/config.properties
      - ../trino_config/catalog:/etc/trino/catalog
      - ../trino_config/coordinator/init.sql:/etc/trino/init.sql
  trino-worker-1:
    image: trinodb/trino:476
    container_name: trino-worker-1
    volumes:
      - ../trino_config/worker/config.properties:/etc/trino/config.properties
      - ../trino_config/catalog:/etc/trino/catalog
    depends_on:
      - trino-coordinator

  trino-worker-2:
    image: trinodb/trino:476
    container_name: trino-worker-2
    volumes:
      - ../trino_config/worker/config.properties:/etc/trino/config.properties
      - ../trino_config/catalog:/etc/trino/catalog
    depends_on:
      - trino-coordinator
```

TL;DR: Trino executes queries via SQL. dbt abstracts away boilerplate SQL
for transformations into a more manageable approach, similar to what ORMs
do for application queries. The difference is in dbt you still have to
write queries BUT it helps in managing query dependencies.

Now, how do we create iceberg table? Easy!

We can easily define the table we want to create as Iceberg. We connect our
Trino cluster to Iceberg connector by simply specifying it in Trino catalog
configuration:

```properties
connector.name=iceberg
iceberg.catalog.type=nessie
iceberg.nessie-catalog.uri=http://nessie-catalog:19120/api/v2
iceberg.nessie-catalog.ref=main
iceberg.nessie-catalog.default-warehouse-dir=s3://local-lakehouse
fs.native-s3.enabled=true
s3.endpoint=http://minio:9000
s3.region=ap-southeast-1
s3.path-style-access=true
s3.aws-access-key=admin
s3.aws-secret-key=password
```

above configuration will tell Trino to:

- Use the Iceberg connector
- Use Nessie as the catalog (for table metadata and versioning)
- Store actual table data in S3-compatible storage (MinIO at `s3://local-lakehouse`)

To make sure dbt uses above configuration, you would have to specify in
Airflow dag to use iceberg profile.

Afterwards, we simply can create the table by running:

```sql
CREATE SCHEMA landing;
CREATE SCHEMA staging;
CREATE SCHEMA curated;
```

Then, to make sure all the Airflow dags are connected into one pipeline:

```yaml
seeds:
  my_dbt_trino:
    schema: landing    # Seeds go to landing layer

models:
  my_dbt_trino:
    staging:
      +schema: staging  # Staging models go to staging layer
    curated:
      +schema: curated  # Curated models go to curated layer
```

Above is basically metadata file to tells Airflow what to run step-by-step.
For the actual data processing, each folder has its .sql file that will be
ran for data processing.

Above is basically metadata file to tells dbt where to materialize each
table. It defines our 3 layer data lakehouse architecture where each layer
is a 'checkpoint' of the state of data.

- **Seeds → Landing Layer:** Raw CSV files are loaded into the landing schema as-is
- **Staging Models → Staging Layer:** Light transformations (cleaning, type casting) go to staging schema
- **Curated Models → Curated Layer:** Analytics-ready tables go to landing schema

For the actual data processing, each folder has its .sql file that will be
ran for data processing.

```
dags/dbt_trino/
├── seeds/                 #CSV files → landing schema
│   └── sales.csv
│       ...
├── models/
│   ├── staging/           # Preprocessing SQL → staging schema
│   │   └── stg_sales.sql
│           ...
│   └── curated/           # Analytics-ready SQL → curated schema
│       └── fact_sale.sql
```

We will not go too details on that, but here is what you need to know —
staging is where we do preprocessing and data that lands in curated table
are ready to be query. We perform reorganize the data into fact table and
dimensional table. To be specific, we change it into STAR schema

```
        dim_product          dim_country
              |                   |
              └─── fact_sale ─────┘
                   (center)
```

- `fact_sale`: Contains business metrics (revenue, cost, profit) with foreign keys
- `dim_product`: Product attributes (name, category, color)
- `dim_country`: Geographic attributes (country, continent)

This design makes it easy for analysts to query sales data by product,
country, or any combination without complex joins.
